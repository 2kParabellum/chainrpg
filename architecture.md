# Architecture

Целевая архитектура кода игры и правила взаимодействия частей.

Этот файл — единственный, где описывается устройство кода. В `game_design.md`,
`characters.md` и `chambers.md` реализация по-прежнему не описывается, там только игровой смысл.

## Зачем это нужно

Игра выросла из одного файла-прототипа. Ближайшие задачи проекта — главное меню,
несколько уровней, прокачка, новые монстры, разные оружия, новые механики. Каждая
из них в монолите требовала копирования или правки логики в десятке мест.
Архитектура решает ровно четыре задачи:

1. Добавление уровня — это новый файл данных, а не копия игровой логики.
2. Добавление монстра, союзника или оружия — это одна новая запись в реестре.
3. Игровой цикл, состояние партии, игровой контент и данные уровня разделены.
4. Всё остаётся простым: vanilla JavaScript, без библиотек, сборки и backend.

## Технические соглашения

- **Обычные `<script src>`, без ES-модулей.** Игра должна открываться и двойным кликом
  по файлу (`file://`), где ES-модули блокируются браузером, и через локальный сервер.
- **Порядок тегов `<script>` в `index.html` — это контракт зависимостей.** Файл может
  пользоваться только тем, что подключено выше него.
- **Один корневой объект-неймспейс** вместо россыпи глобальных имён: каждый файл вешает
  своё на общий объект игры. Это не фреймворк, просто один корень.
- Никаких библиотек, бандлеров, TypeScript, npm и backend. Рендер — HTML Canvas,
  только геометрические фигуры.

### Шаблон файла

Каждый файл в `src/` устроен одинаково:

```js
(function (G) {
'use strict';
const { CONFIG, state } = G;          // зависимости — деструктуризацией в самом верху
const { dist } = G.math;
...код модуля...
G.combat = { damageUnit, ... };       // публичный интерфейс — одной строкой в самом низу
})(window.Game = window.Game || {});
```

- Зависимости файла видны с первых строк. Если нужного модуля нет среди подключённых
  выше — это нарушение порядка слоёв, а не повод достать его через `window`.
- Тело файла не сдвигается на уровень вправо, чтобы код читался как обычный файл.
- `'use strict'` включён: обращение к необъявленной переменной падает сразу, а не создаёт глобал.

### Ключи неймспейса

`G.CONFIG`, `G.COLORS` — параметры и палитра. `G.math`, `G.collision` — чистые функции.
`G.weapons`, `G.allyTypes`, `G.enemyTypes` — реестры оружий и типов. `G.input` — ввод. `G.level1`, `G.level2`, `G.populate` — данные
уровней и заселение. `G.world` — геометрия.
`G.state` — **только данные** партии: цепочка `state.party` (первое звено — ведущий), цель движения
`state.moveTarget`, огни `state.fires` и остальные списки. `G.session` — функции над ними (создать юнита,
сбросить партию, ведущий `leader()`, цепочка юнитов, режим звена и его оружие, источники света, текущая комната). `G.chain`, `G.combat`,
`G.roaming`, `G.update` — игровая логика. `G.shapes`, `G.renderer`, `G.hud` — вывод.

## Слои и структура

Пять слоёв, зависимости идут строго сверху вниз.

```
index.html
src/
  config/     тюнинг и палитра        — ни от кого не зависит
    tuning.js       общие параметры: мир, ведущий, свет, шипы, огонь, цепочка, реген
    palette.js      цвета

  core/       фундамент               — зависит только от config
    math.js         чистая математика без состояния
    collision.js    круг-прямоугольник, движение со столкновениями, отрезок-прямоугольник
    input.js        мышь и клавиатура -> намерения игрока: команды с необязательным аргументом
                    (цифра 2..9 — «сменить ведущего», аргумент — номер звена); координаты уже в системе канваса

  content/    игровой контент         — зависит от config и core
    weapons.js      реестр оружий и умений (меч, лук, щит, сапоги, огонь…); подключается раньше allies.js
    enemies.js      реестр типов врагов (мина — тоже запись, с флагами)
    allies.js       реестр типов союзников: тело, оружие по режимам «с факелом» / «в цепи»

  levels/     данные уровней          — зависит от config, core, content
    level1.js       «Learn the Ropes»: 12 комнат в линию, планировка, пулы типов, правила состава, старт Героя, условие победы
    level2.js       «Playground»: поле из сетки зон, планировка зон, порталы, правила состава, старт, условие победы
    populate.js     заселение точек уровня по его правилам; союзники раскладываются одним броском на весь уровень

  game/       игровая логика          — зависит от всего вышележащего
    world.js        геометрия мира и запросы к ней (линия комнат или поле из зон), шипы по клеткам
    state.js        состояние партии целиком, её сброс, создание юнитов и врагов, свет
    chain.js        цепочка: след, следование, вербовка, бросок, нокаут, смена порядка и ведущего, модель меню порядка
    combat.js       урон, снаряды, щиты, взрывы, огни на земле, эффекты, средовой урон
    roaming.js      общие движения врагов: блуждание по комнате, сход с шипов, погоня за игроком
    update.js       порядок обновления кадра, движение ведущего, правила партии

  render/     вывод                   — читает состояние, но не меняет его
    shapes.js       примитивы отрисовки
    renderer.js     отрисовка мира и сущностей
    hud.js          интерфейс, меню порядка цепочки, экраны исхода, затемнение (по всем источникам света)

  main.js     бутстрап, игровой цикл, смысл намерений ввода, список уровней и их выбор, экраны
              (state.status — единственный источник правды)
```

### Ответственность модулей

- **config/tuning.js** — параметры, не привязанные к конкретным типам сущностей.
  Важно: размер комнаты и размер вьюпорта — **разные** параметры, даже если сейчас совпадают.
- **config/palette.js** — все цвета игры.
- **core/math.js**, **core/collision.js** — чистые функции. Не знают ни про мир, ни про состояние.
  В `math.js` лежат и мелкие общие помощники: случайный выбор, перемешивание, удаление из списка.
- **core/input.js** — единственное место, где игра слушает мышь и клавиатуру. Превращает
  события в намерения (идти в точку, подобрать, бросить, сменить ведущего, открыть меню, рестарт) и больше ничего не решает.
- **content/weapons.js** — реестр оружий. Одна запись = одно оружие или пассивное умение: стартовые
  характеристики и поведение за кадр (`update`), при необходимости — перехват вражеского снаряда (`block`, у щитов)
  и рисование (`draw`). Оружие получает от игры сервисы параметром `game` и не подключает `game/` и `render/`.
  У каждого носителя своя копия оружия с личной перезарядкой.
- **content/enemies.js**, **content/allies.js** — реестры типов. Один тип = одна запись,
  в ней лежат характеристики, поведение и отрисовка этого типа. Это главный модуль
  для расширения игры новыми сущностями. Список полей записи — в шапке каждого файла.
  Записи не подключают `game/` и `render/`: всё нужное они получают параметром —
  `game` (сервисы игры, собирает `game/update.js`) и `g` (примитивы рисования из `render/shapes.js`).
  Особенности типа задаются полями записи, а не проверками по имени типа в общем коде.
  Союзник описывается телом (имя, HP, радиус) и **двумя режимами**: `lead` (звено идёт первым: радиус света
  и оружие) и `chain` (звено идёт следом: оружие), плюс пассивные `traits` и флаг `anchor` (Герой: нельзя
  выбить, смерть — поражение). Режим определяется местом в цепочке, а не самим юнитом.
  Сюда же относится портал: он — обычная запись врага с флагами `noRegen` и `alwaysActive`,
  порождает врагов через `game.spawnEnemy` (темп берёт из таблицы `spawnEvery` по числу живых порталов, предел охотников на карте — `maxHunters`) и выбирает типы из `game.chaserTypes` — всех записей,
  у которых есть `chaseSpeed` (то есть подвижных). Порождённый враг получает поле `hunter`,
  и поведение записи (шаблон стрелка, бычок, зомби) вместо блуждания зовёт `game.chaseStep`.
- **levels/level1.js, levels/level2.js** — данные одного уровня: название и описание для меню,
  геометрия (`kind`: `line` — комнаты в линию, `field` — поле из сетки зон), планировка комнат
  или зон, правила случайного состава, старт Героя (`spawn: { room, at }`), условие победы
  (`victory.kind`: `clearFinalRoom` — дойти до последней комнаты и перебить всех, `destroyType` —
  разрушить всех врагов заданного типа). Игровой логики здесь нет. Уровень передаётся
  в `resetGame(level)` и лежит в `state.level`; код, которому нужны данные уровня, берёт их оттуда,
  а не подключает файл конкретного уровня. Необязательные поля уровня, которые читает интерфейс:
  `zoneNames` (названия зон в строке состояния) и `victory.label` (подпись счётчика цели). Уровень может задать веса типов врагов `enemyWeights` (влияют на состав зон и на выбор типа, который порождает портал) и свой предел цепочки `maxParty` (число тел вместе с ведущим); без него действует общий из `config/tuning.js`.
- **levels/populate.js** — общий для всех уровней код заселения: разложить типы по точкам
  по правилам уровня и создать сущности. Союзники уникальны, поэтому их состав бросается **одним броском на весь
  уровень** (сначала `require` комнат, затем остальные места берут ещё не занятые типы): точки комнат и
  `scatterAllies` — союзники, разбросанные по случайным местам указанных зон (заселение выдаёт список [тип, зона],
  точку подбирает `state.js`). Враги комнаты задаются либо точками (`spots`), либо
  числом (`count`): во втором случае точки в результате не указаны, и их подбирает `state.js`
  по реальной геометрии. У точек союзников есть необязательный `chance` — вероятность появления.
- **game/state.js** — единственный объект, в котором лежит вся партия: цепочка (`party`, первое звено —
  ведущий), цель движения, нейтралы, лежачие, враги, снаряды, эффекты, облака, огни, след, камера, исход.
  Здесь же сброс партии, создание юнитов (`makeAlly` копирует в юнит тело и оружие обоих режимов, у одинакового
  оружия одна копия на оба режима), создание врага посреди партии и свет: радиус факела берётся у ведущего,
  огни Факира — дополнительные источники (`lightSources`, `isLit`).
- **game/world.js** — вся статическая геометрия: сборка мира из уровня, пересчёт координат
  комнаты, номер комнаты по точке, прямая видимость, запросы про шипы и свободные точки
  (`scatterSpot` — для стартовой расстановки, `freeSpotNear` — куда встаёт порождённый враг), длина луча
  до стены (`rayLength`). Шипы хранятся клетками: `trampleSpikes` убирает клетки под кругом (сапоги Воина).
  «Комната» для остального кода — это и комната линейного уровня, и зона поля: номер и внутренний
  прямоугольник. **Всё знание о раскладке — что комнаты стоят в линию или что мир — сетка
  зон со стенками на стыках — живёт только здесь.**
- **game/chain.js** — цепочка как механика: след ведущего, следование звеньев, вербовка,
  бросок, выбивание и протяжка лежачего (только рядовых: ведущего и Героя вытеснить нельзя),
  порядок звеньев: одна операция «поставить в новый порядок» (`applyOrder`) обслуживает и клавиши 2–9,
  и меню; при смене ведущего звенья меняются местами на полу, скорость и направление переходят новому.
- **game/combat.js** — всё, что наносит урон: снаряды (в том числе навесные — горшок Факира), взрывы по площади,
  перехват снарядов щитами, огни на земле, эффекты, шипы, облака, смерть сущности (смерть ведущего перестраивает след).
- **game/update.js** — порядок кадра явным списком, движение ведущего и правила партии: оружие звена
  работает по его режиму (ведущий — `lead`, остальные — `chain`), пассивные особенности всегда; активация врагов
  (по расстоянию до ведущего; порталы и охотники активны всегда), победа по правилу уровня,
  поражение (смерть Героя), камера по обеим осям.
- **render/** — только вывод. Читает состояние, никогда его не меняет.
- **main.js** — игровой цикл, смысл намерений ввода (что значит «подобрать», «бросить», «сменить ведущего», клик по меню),
  список уровней (`LEVELS`) и их выбор из главного меню, кнопка возврата в меню, экраны.
  Оверлей главного меню в HTML только отражает `state.status`; кнопки выбора уровня строятся
  из списка `LEVELS`.

## Правила зависимостей

1. Зависимости идут только вниз по списку слоёв. `core` не знает про `game`,
   `content` не знает про `levels`, `game` не знает про `render`.
2. **`render` не меняет состояние.** Любая мутация из рисующего кода — ошибка.
3. **`game/world.js` — единственный владелец знания о раскладке мира.** Если нужна
   геометрия, спрашиваем у него, а не пересчитываем формулой на месте.
4. **Состояние партии живёт только в `game/state.js`.** Модули получают его аргументом
   или читают у него, но не заводят собственных копий игровых списков. Сброс партии
   подменяет массивы целиком, поэтому обращаться к ним нужно всегда как `state.party`
   в момент использования — списки нельзя сохранять в локальные переменные модуля
   и нельзя деструктурировать из `state` при загрузке файла. Единственное исключение из «мир — статика» —
   шипы: растоптанные Воином клетки убираются из `world.spikes`, потому что это геометрия мира; мир пересобирается
   при сбросе партии, и шипы возвращаются.
5. **Тип сущности не знает про другие типы.** Если поведению нужны чужие параметры
   (например, лежачего тащит скорпион), эти параметры записываются в саму сущность
   в момент события, а не читаются из чужого конфига.
6. **Характеристики копируются в сущность при создании**, а не берутся ссылкой на реестр.
   Иначе любая прокачка изменит характеристики сразу у всех сущностей этого типа. Это касается и оружия:
   у каждого юнита свои копии оружия обоих режимов, с личными перезарядками.
7. **Режим звена определяется его местом в цепочке.** Юнит не хранит «я ведущий»: код спрашивает `modeOf(u)`.
   Ведущим может быть любой; всё, что зависит от того, кто впереди (свет, камера, цель охотников, активация),
   спрашивает `leader()`, а не ищет Героя.
8. `levels` содержит данные, а не логику. Логика, общая для уровней, живёт в `populate.js`.

## Как расширять игру

- **Новый монстр или союзник** — одна запись в реестре `content/`: характеристики,
  поведение, отрисовка. Существующий код не трогается. Если тип нужен в случайном
  составе комнат, он добавляется в пул нужного уровня.
- **Новый уровень** — новый файл в `levels/` с планировкой и правилами, тег `<script>` в `index.html`
  и строка в списке `LEVELS` в `main.js` (кнопка в меню появится сама). Игровая логика
  не копируется. Если уровню нужна геометрия другой формы, меняется только `game/world.js`;
  если нужен новый вид условия победы — правило в `game/update.js` и, при необходимости, строка
  состояния в `render/hud.js`.
- **Новое оружие** — одна запись в `content/weapons.js` (характеристики, `update`, при необходимости
  `block` и `draw`); персонаж подключает его в нужный режим записью в `allies.js`. Общим шаблонам (ближний
  удар, выстрел по освещённому) уже есть функции в шапке файла.
- **Новый союзник** — запись в `allies.js` (тело, два режима, знак) и цвет в палитре; чтобы он встречался на
  уровне, его добавляют в `allyPool` уровня.
- **Прокачка** — опирается на правило 6: характеристики у каждой сущности свои,
  поэтому их можно менять поштучно.

## Инварианты, которые нельзя ломать

- **Порядок обновления кадра фиксирован**: ведущий (движение), след, затем звенья цепочки (ведущий первым),
  лежачие, враги, снаряды, облака, огни, шипы, мины. Перестановка меняет баланс.
- Список освещённых врагов считается один раз за кадр **до** обновления звеньев —
  дальнее оружие стреляет только по нему (свет: факел ведущего и огни Факира).
- Сущность, меняющая роль (нейтрал -> звено цепочки -> лежачий -> звено), сначала убирается
  из старого списка, потом меняет роль, потом добавляется в новый.
- Героя из `state.party` не убирают даже после смерти: партия заканчивается, а сцена и камера
  не остаются без ведущего.
- Списки сущностей перебираются по копии, если внутри цикла кто-то может умереть.
- Порядок создания сущностей при старте партии влияет на случайный расклад.
  Менять его без причины нельзя. В пределах комнаты: союзники, порталы, враги, мины
  (порталы идут раньше врагов, чтобы те расставлялись мимо них); разбросанные союзники
  ставятся после всех комнат. Состав союзников бросается до расстановки комнат, одним броском на уровень.
- Мина — особый враг: не блуждает, не действует сама, не попадает в счётчик врагов,
  не мешает победе, видна и атакуема только после обнаружения. Эти свойства задаются
  флагами в её записи в реестре, а не условиями по всему коду.

## Чем реальный код пока отличается от схемы выше

Три этапа переноса завершены, целевая структура достигнута; второй уровень (поле, порталы, выбор уровня
в меню) уложился в неё без новых слоёв. Остаётся один известный пробел.

| Что | Сейчас | Цель |
|---|---|---|
| Снаряды и эффекты особых видов | Гарпун, навесные снаряды (катапульта, горшок Факира), облако, огонь на земле и их отрисовка живут в `game/combat.js` и `render/renderer.js`; облако читает параметры Зомби из реестра | Новый вид снаряда не требует правок общего кода |

Также пока нет: возобновления партии после возврата в главное меню (кнопка «МЕНЮ» бросает партию),
системы прокачки.

## Чего в архитектуре сознательно нет

ECS, dependency injection, event bus, scene-граф, машины состояний как фреймворка,
сборки, тестового фреймворка, пулинга объектов, пространственных индексов для
столкновений, поиска пути. Проект маленький, всё перечисленное стоит дороже, чем
решает. Если что-то из этого понадобится — сначала доказательство необходимости,
потом правка этого файла.
